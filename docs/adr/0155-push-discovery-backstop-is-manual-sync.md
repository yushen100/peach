# ADR-0155：推送发现漏掉的文件由手动同步补齐，不设定期全量扫描

- 状态：已采纳
- 日期：2026-11-08
- 关系：部分取代 [ADR-0041](0041-new-files-are-pushed-in-scanning-is-the-backstop.md) 第七条；其余各条不变

## 背景

ADR-0041 第七条写的是「漏发由定期全量扫描补上，扫描照常跑，它仍是『账本与盘一致』的那个保证」。2026-11-08 的全库排查核对了实现：应用里没有任何定时扫描作业，后台调度只有自动更新、关注抓取、升级补修与任务恢复；本机也没有外部计划任务替它扫描。也就是说，这条保证从 ADR-0041 落地起就不存在，`docs/OPERATIONS.md` 与 `docs/CLOUDDRIVE.md` 却一直按它来写。

同一轮排查还发现推送发现的待办只在内存里，服务一重启，已收到、还在等文件写完的路径就丢了。这一项已在 #506 改为落盘（`push-discovery-pending.json`），重启后接着登记。

定期全量扫描本身的代价没有变：`A:`、`B:` 是 CloudDrive 挂载，每次列目录都是网络请求，本机误判过一次，一轮遍历读掉 167 GB。ADR-0041 把扫描频率钉在「不能勤」，正是因为这一点。

## 决策

**一、不设定期全量扫描。** 推送发现漏掉的文件，即事件风暴丢事件、CloudDrive2 在 Peach 停机时推空、前缀表配错漏掉的那一类，由用户在界面上点「同步新增文件」补齐。它只枚举目录、跳过已知路径的逐文件属性读取，比全库维护轻得多。

**二、能自己补的先自己补。** 已收到的推送先落盘再登记，重启接着做（#506）；等文件写完超时的路径照旧放弃，留给「同步新增文件」。

**三、文档按实际行为写。** 运维文档与 CloudDrive 文档不再称有定期扫描兜底，写明停机或漏发期间新增的文件要靠「同步新增文件」。

## 被否决的方案

- **按 ADR-0041 原意补一个定时全量扫描。** 网盘挂载上一轮遍历就是几十到上百 GB 的列目录流量，频率只能很低，低到几天一次时它补漏的作用和用户手点一次「同步新增文件」差不多，却要多承担一次无人值守的大流量遍历。
- **只对本地盘定期扫描。** 本地盘已经有 watchdog 实时订阅，漏事件的主要来源是网盘一侧，只扫本地盘补不到要补的那部分。

## 后果

- 账本与盘一致不再有自动保证：推送没配、Peach 停机或推送漏发时，新文件要等用户点「同步新增文件」才出现。
- 不新增调度作业，不新增网盘流量。
- 以后若要恢复自动补漏，须新增 ADR 说明频率、来源范围与流量预算。
