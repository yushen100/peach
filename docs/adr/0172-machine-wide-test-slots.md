# ADR-0172：正式测试入口按整机名额排队

- 状态：已采纳
- 日期：2026-11-16
- 关系：修订 [ADR-0128](0128-test-selection-contracts-and-verified-mainline.md) 第 4 条「正式入口不取得机器级资源锁」；仓库全量锁、集成锁与 [ADR-0121](0121-release-rehearsal-and-atomic-publication.md) 的发布流程不变

## 背景

2026-10-24 起测试入口曾取得一把整机重负载锁：全量、含浏览器用例的运行与本机 CI 作业全部串行。几个会话各自交付时，排在后面的任务要等前面每一轮全量跑完，交付明显变慢。ADR-0128 第 4 条在 10-27 去掉了这把锁，只保留同一仓库全量验证与集成互斥的 `full-suite.lock`。

去掉之后，多个会话在本机同时跑 `auto`、`full` 与浏览器 e2e。2026-11-16 实测整机 CPU 97%、内存 84%，有时限的用例（服务就绪、vitest worker、浏览器等待）因此超时失败。各会话把这些失败当成代码问题排查，花在不存在的问题上的时间比排队还多，测试结论也不再可信。

## 决策

1. **正式入口按整机名额排队，不全部串行。** 名额默认 2 个，可用环境变量 `PEACH_TEST_SLOTS` 调整。名额目录在用户目录下，本机所有检出与工作树共用：Windows `%LOCALAPPDATA%\peach-test-locks\slots\`，macOS/Linux `~/.local/state/peach-test-locks/slots/`。
2. **按预计负载占名额。** 待跑文件按本机实测秒数估计的串行耗时达到全量的 60% 时（新开的 `full` 总是达到），从 1 号起按顺序逐个取满全部名额；其余 `auto`、显式域与续跑取 1 个；含浏览器 e2e 文件或超过 10 个测试文件的 `-Focus` 取 1 个；最多 10 个 Python 或 Vitest 文件的 `-Focus` 不占。复用有效记录、CI 作业，以及持有名额的运行派出的分片与隔离重跑都不排队。
3. **按到达先后排队。** 复用 `full-suite.lock` 的排队票：排在最前面的才去取名额；全量只取到一部分时继续留票，后到的运行不插队。等待时每分钟打印各名额的范围、pid、工作树路径、开始时刻与已运行时长。排队不设时限，测试入口等 `full-suite.lock` 也取消原来的 30 分钟上限；`full-suite.lock` 对代码一致性的互斥照旧。
4. **进程退出即收回。** 名额是操作系统文件锁，持有进程退出或被强行结束就释放；pid 已退出或已被复用的持有记录不再报出。
5. **锁的顺序固定。** 先取 `full-suite.lock`，再取同状态验证锁，最后取整机名额；持有名额的运行不再等待别的锁。多个名额只按编号顺序取，两个全量不会各占一部分互相等待。
6. **隔离重跑在名额内进行。** 失败文件的单独重跑沿用本次运行持有的名额，此时本次分片都已结束；没有名额的定向调试先排 1 个再重跑。
7. **名额设置不进测试记录的环境指纹。** `PEACH_TEST_SLOTS` 与持有标记 `PEACH_TEST_SLOTS_HELD` 只决定何时开跑，不改变被验证的环境；名额设置不同的会话仍承认彼此的记录，`ready` 与 `integrate` 不因此拒收。

## 理由

- 名额比整机串行宽：两个 `auto` 或定向浏览器调试可以同时跑，只有全量独占整机。比完全不限制严：同时运行的重负载最多两份，有时限的用例不再被挤到超时。
- 等待的时间换来可信的结果。一轮时序误报会让一个会话重跑全量、排查不存在的问题，耗时远超排队；排队时打印占用者，等待者能判断要等多久。
- 按标签判重量会漏：近两周本机跑了 200 个以上测试文件的 258 次运行里，约 141 次没有标 `full`。按实测秒数估计，`auto` 选中多个域时同样占满。
- 等锁上限比全量本身还短时（`full-suite.lock` 30 分钟，全量 p90 约 55 分钟），排在后面的运行注定超时退出，两周内有 8 次；排队按先后一直等，结果更可预期。
- 偶发失败的隔离重跑如果仍在高负载下进行，会把真问题判成偶发，或把偶发再判一次失败；在名额内重跑才能区分两者。
- 小范围的 Python 与 Vitest 定向调试负载低，调试循环频繁，排队的代价大于它带来的资源争用，所以不占名额。

## 后果

- 本机同时只有一轮全量。多个工作者并行时，工作者只跑定向测试，`auto` 与 `full` 由集成分支统一跑一轮；排队是正常现象，不调 `PEACH_TEST_SLOTS` 插队。
- 时序类失败先看名额占用与 `agent_worktree.py processes`，再判断是否是代码问题。
- ADR-0121 所说的整机重负载锁由整机名额取代。`scripts/machine_lock.py` 改为取满全部名额，GitHub 托管 runner 每个作业一台机器，CI 上不排队，也不依赖名额目录存在；自托管 runner 若恢复使用，仍用它包住构建与冒烟，与本机测试排同一组名额。
- 持有者卡住时等待者会一直等；每分钟的占用报告给出 pid 与工作树，由人判断是否结束它。
- 名额只约束经测试入口或 `machine_lock.py` 的运行；开发者手动启动的构建、预览服务与浏览器不受约束。
