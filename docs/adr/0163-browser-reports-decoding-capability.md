# ADR-0163：浏览器报告解码能力，服务端据此直放、换封装或转码

- 状态：已采纳
- 日期：2026-11-15
- 关系：部分取代 [ADR-0016](0016-remote-mp4-default-range-hls-opt-in.md) 的第三、四条（不做服务端编码探测、不为 HEVC 转码）；ADR-0016 的 HLS 按需模式仍然有效

## 背景

ADR-0016 写的是：服务端不探测编码，能不能播交给浏览器，不支持 HEVC 的浏览器直接报错。2026-09-05 为了让不支持
HEVC 的浏览器也能播，服务端加了 ffprobe 编码检查（`TranscodeService._browser_compatible`）：MP4 里只有
H.264 8 位配 AAC/MP3 直放，其余一律转码。这一步推翻了 ADR-0016 的两条，当时没有记录。

结果是 HEVC 对所有浏览器都转码，包括本来就能硬解的 Safari、带硬解的 Chrome 和 Edge。低功耗 NAS 上 libx264
跟不上实时速度，播放器卡在第一个分片（#616）。服务端知道片子是什么编码，但不知道对面的浏览器能不能解；
ADR-0016 说的「浏览器的能力才是判决」仍然成立，缺的是把能力告诉服务端。

## 决策

**一、浏览器报能力。** 播放器在页面里探测一次：`video.canPlayType` 对 `hvc1` 主档、Main10 档和 `hev1`
标签的回答，有 `navigator.mediaCapabilities` 时再用 `decodingInfo` 确认。结果作为 `decode=hevc,hevc10,hev1`
带给 `/api/stream-plan`，计划回的 `/stream` 地址带同一个参数。不认识的项丢掉；不带参数（旧前端、外部播放器、
卡片悬停预览）就是什么都不报，行为和此前完全一样。

**二、服务端按能力分流，只改判断不改命令。** MP4 里的 HEVC：

| 情况 | 结果 |
| --- | --- |
| 报了 `hevc`；10 位另需 `hevc10`；`hev1` 标签另需 `hev1`；音轨 AAC/MP3/无 | 原文件 Range 直放 |
| 视频能解，只差音轨或 `hev1` 标签 | `/stream` 整片换封装：视频复制、标签改 `hvc1`、音轨转 AAC；产物文件名带 `-copy`，和转成 H.264 的那份分开 |
| 杜比视界（`dvh1`/`dvhe`）、4:2:2、4:4:4，或浏览器没报 | 照旧转码 |

H.264 的判断不变。MKV 等非原生容器不在本 ADR 范围内，仍按原路转码。

**三、报能解却解不出来时自动回退。** 起播后报 `MEDIA_ERR_DECODE` 或 `MEDIA_ERR_SRC_NOT_SUPPORTED`，或者
4 秒内播放时间前进超过 1 秒但一帧都没解出来（`getVideoPlaybackQuality().totalVideoFrames`，Safari 用
`webkitDecodedFrameCount`；或 `videoWidth` 仍为 0），播放器在本机记下「这台浏览器直放 HEVC 失败」30 天，
重新要一次不带 `hevc` 的计划，从原位置接着播。同一次播放只回退一次。

**四、留一个设置作兜底。** 「浏览与播放 → 播放」里的「HEVC 播放方式」：自动（按浏览器能力，默认）、总是转码、
总是直放。它只改浏览器报给服务端的能力：总是转码就不报 `hevc`，总是直放就把三项都报上，服务端不另存设置。
理由：探测和回退能处理绝大多数情况，但有两类是它们看不见的——浏览器报能解、也解出了帧，画面却花屏或偏色（驱动
问题），以及用户宁愿多等转码也要省电或省流量；反过来，探测保守地报不能解、而用户确知能播时，「总是直放」省掉
一次转码。按浏览器存，同一个人在不同设备上可以各选各的。

## 放弃方案

- **服务端全局开关**（#616 的 `PEACH_BROWSER_DECODE`）：开关在服务端，同一时间不同浏览器的能力不同，总有一边错；
  打开后不支持的浏览器只剩报错，没有回退。
- **只靠 `canPlayType`**：Edge 在部分版本、Chrome 在驱动太旧时会报能解却解不出，必须有第三条的回退。
- **HEVC 也走 HLS 复制分片**：Chromium 的 MSE 不支持 TS 里的 HEVC（ADR-0016 背景），Safari 的 HLS 只接 fMP4
  里的 HEVC；为此改分片格式超出本 ADR。

## 后果

- 能硬解 HEVC 的浏览器播 HEVC MP4 不再占服务端 CPU，也不再写整片转码缓存。以前为这些片子转好的 H.264 缓存不再
  命中，由存储预算按最久未用清理，不需要迁移。
- 同一部片在不同浏览器之间交替播放时，`-copy` 产物和 H.264 产物会互相替换：整片缓存仍是每部片只留最新一份。
- 回退判据依赖播放器换源，详情与沉浸两处播放器各接一次。
- 真机验证（iPhone Safari、Mac Safari、有无 HEVC 硬解的 Windows Chrome、Android Chrome、NAS 上的 CPU 占用）
  不能用 headless Chromium 代替，headless 的 HEVC 支持随平台变化。
